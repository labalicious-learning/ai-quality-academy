Prepare a project review

Give your reviewer a clear question, a frozen version and evidence they can inspect.

Private preparation → deliberate sharing. Nothing is uploaded or posted. This creates a project-review note, not a complete lab submission, grade or certificate. Your planner feedback stays out. Links and commits are not fetched or verified.

Start with a milestone. Only choose evidence you intend to share.

1 · Freeze the context

In each trusted local repository, run git rev-parse HEAD. Confirm the project commit is pushed and contains the evidence you reference. A SHA alone does not prove that work was reviewed.

2 · Tell the reviewer what matters

Use fictional data and repository-relative artifact paths. Be specific and honest: “not run yet” is better than an invented result. These fields will all be shared.

3 · Choose evidence explicitly

References come from saved planner entries for this milestone. None are selected automatically. Notes remain private unless you tick their separate inclusion box. Linked files must also be inspected for public safety.

Unfinished public-facing fields can be recovered in this browser. Evidence choices and sharing approval are never recovered.

4 · Inspect the exact Markdown

The privacy check only catches some obvious mistakes. Read every line and inspect linked content yourself. Local drafts are plaintext browser data, not encrypted storage.

Download is not submission. Inspect the saved file, then attach it to your project’s review PR or use the instructor-approved channel. The normal lab intake still requires its manifest, evidence files and AI-use note.
